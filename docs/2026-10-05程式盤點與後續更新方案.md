# 程式盤點與後續更新方案

盤點日期：2026-10-05  
盤點範圍：網站程式、公開資料建置、Google 試算表更新流程、現有檢核與維護紀錄。第一階段已加入資料預檢與介面可用性修補；沒有修改賽果內容。

## 現況摘要

- 網站是純前端靜態網站，GitHub Pages 提供公開頁面；沒有自建資料庫或後端。`data/public-data*.csv` 是正式來源，`tools/build_data.py` 產生 `data/public-data.js`、`calendar.ics`、SEO 摘要和更新報告，再由前端讀取。
- 專案包含 45 個賽事 CSV；目前生成資料檔約 1.1 MB。`data/update-report.txt` 最新記錄為 2026-10-04，列出 1,410 場戰績、399 筆榮譽、48 筆辯題、306 個單位及 109 隊公告名單。
- 首頁快照是每個瀏覽器各自保存的公開首頁 HTML，最多保存 30 日。它能改善同一裝置回訪時的等待感；新裝置、首次造訪、快取失效時仍要完整讀取資料。
- 目前有 16 個 Python 單元測試，涵蓋日期、數字、題解、來源選擇、資料檢核及行事曆輸出。已新增資料檢查工作流程，在符合範圍的推送與 PR 執行預檢及單元測試。

## 需要優先處理的風險

### 1. 資料檢核目前偏向欄位檢查，錯誤值可能帶進正式資料

`tools/build_data.py` 現已提供唯讀預檢，會拒絕無效數字、日期格式錯誤、單邊比分、無效資料類型及不屬於該場雙方的勝方；比分與勝方矛盾會產生提醒。預檢可核對賽事 metadata 日期、未來賽事的日期與重要時程，以及同賽事／日期／時段／會場／兩隊配對的場次碰撞。配對比較保留 A、B 隊區別，不自動合併任何紀錄。

另外已唯讀掃描現有 1,410 場戰績：沒有相同賽事、日期、時段、會場及兩隊配對的衝突。另有兩組「同場地時段但隊伍不同」的紀錄，不能當作重複場次自動修正：火雞盃 2026-04-26 時段四會場一列有四強分流與冠亞賽；2024 明京盃 8 月 24 日時段三會場一的來源備註指出賽果來自另一則公告。只用同日與兩隊配對會誤抓 104 組合法不同時段對戰，因此不採用該規則。

這代表建置成功不一定代表每筆資料都已通過一致性核對。`update-report.txt` 的「沒有提醒」只代表目前檢查器沒有觸發既有規則，不等於全站資料已逐筆人工查證。

### 2. Google 試算表更新不會以使用者的 Google 帳號編輯資料

目前 GitHub Actions 以公開匯出網址下載指定試算表，再呼叫同一個建置程式，最後由工作流程把生成檔直接提交至 `main`。它沒有 Google OAuth 或使用者帳號授權，也不會把網站回報寫回試算表。是否能下載取決於該試算表的分享權限；網址可讀取不等於私有內容或個人帳號代編。

工作流程具備 `contents: write`，且使用第三方自動提交 Action 的版本標籤；匯入完成後沒有獨立人工差異審查步驟。現已加入資料預檢，並把 `calendar.ics` 納入提交清單；仍需考慮將匯入改成產生 PR，讓資料差異可先檢閱再進主分支。

### 3. 首頁快照是體感改善，不是完整載入效能改善

`data/public-data.js` 約 1.1 MB，前端仍以一般同步 script 載入整份資料，所有主要畫面共用同一份資料。快照只在本機已有成功快取時先呈現上一版首頁，最新資料載入後再更新；它無法幫助首次造訪、跨裝置同步或縮短完整資料下載與解析時間。使用者看到的短暫舊資料是預期行為，更新失敗時會保留舊內容並提示。

目前沒有正式冷啟動／回訪行動網路量測，因此還不能判斷瓶頸主要在下載、JavaScript 解析、畫面重繪或裝置效能。

### 4. 使用者自己的建檔紀錄沒有雲端備份

選手和隊伍建檔保存在瀏覽器 `localStorage`，不是公開資料庫，也不會自動同步到另一部手機或電腦。清除網站資料、換瀏覽器或換裝置可能失去資料；需依介面匯出 CSV 自行備份。

## 建議更新方案

### 第一階段：先讓每次資料更新可檢查、可回復（已完成核心項目）

1. 已加入唯讀預檢；建置前攔截錯誤資料，並讓比分與勝方矛盾以提醒呈現。
2. 已檢查日期格式、兩邊比分成對、勝方與隊伍／別名一致、賽事 metadata 日期、未來賽事重要時程，以及精確時段／會場／隊伍配對衝突。候選只提醒、不自動合併；更完整榮譽／題解語意檢核列入後續。
3. 名稱歸戶衝突應顯示原始名稱、正式名稱與來源列；不要自動合併需要人工判斷的學校或隊伍。
4. 更新報告列出錯誤、提醒、被略過列及生成前後筆數差異；日常校對優先看差異，不需要每次重讀全站所有資料。
5. 保持現有 CSV 為主來源；每次新增／修正先看預檢報告與網站預覽，確認後再推送。誤更新時以 Git 還原最近一次正確生成結果。

驗證結果：`python3 tools/build_data.py --check --fail-on-warnings` 通過；目前 45 個賽事、1,410 場戰績、399 筆榮譽、48 筆辯題，無提醒。`python3 -m unittest discover -s tests` 通過 16 項測試。行事曆測試涵蓋日期順序、重要時程、UTF-8 折行、特殊字元跳脫與 CRLF；資料檢核測試涵蓋疑似重複場次及 A／B 隊保留。

### 第二階段：讓自動更新保持方便，但避免錯誤直上公開站

1. **下一個優先工作：自動更新先產生可審查差異。** 摘要至少列出賽事、場次、榮譽、辯題、名單、單位數的增減與警告；把目前直接提交 `main` 的匯入流程改為建立 PR，檢查通過後再合併部署。
2. 檢核錯誤時停止流程；提醒則保留人工檢視入口。需由具 repository 權限的人觸發更新，外部網站訪客仍不能改 repository。
3. 將 Google 試算表的可見範圍視為明確的資料分享決策；若要保密，改用受控憑證或私人匯入流程，而非公開匯出連結。
4. 逐步把第三方 Action 固定到經核對的 commit 版本，並維持工作流程只具備更新所需的最低權限。

### 第三階段：按實際手機量測處理首頁等待

1. 分別量冷啟動、同裝置回訪、行動網路與更新失敗時的載入情況；特別確認快照是否能在完整資料下載期間先被瀏覽器繪出。
2. 保留快照作為回訪的容錯層，明確讓首頁資料標示「更新中」或舊資料保留狀態，避免使用者把舊快照當成剛更新的版本。
3. 若完整資料仍是瓶頸，再考慮先載入首頁必要摘要、其他詳情延後載入，或將生成資料改成可快取的 JSON 分片。先量測再拆分，避免增加部署與資料一致性的複雜度。

建議先完成冷啟動與回訪的真實手機量測，再決定是否拆分資料。首頁快照已存在，重做快取機制的優先度低於量測與資料更新審查。

### 第四階段：逐步補齊前端維護與手機檢查（本輪已完成可用性修補）

1. 已修補鍵盤焦點、頁面切換焦點、搜尋框焦點提示、分頁鍵盤操作及減少動態效果偏好；Safari 預覽確認桌面互動及窄螢幕斷點無水平溢出。
2. 已為未來賽事加入日期順序、重要時程日期／時間與重複識別檢查，並測試 ICS 的 CRLF、UTF-8 行長折行及特殊字元跳脫。後續可為快照補上過期、儲存不可用及資料載入失敗行為檢查。
3. 有穩定檢查後再考慮逐步拆分大型 `app.js` 與 `styles.css`。目前純前端、無框架的結構部署簡單，不建議先為了重構而引入大型建置工具。
4. 保持建檔 CSV 匯出提醒；若未來要跨裝置同步，需另行設計登入、權限、備份與個資管理，不能只把 `localStorage` 改成公開雲端表格。

## 建議的每次更新步驟

1. 收到公告、簡章或使用者回報，保留原始來源與來源類型。
2. 依賽事登錄模板整理草稿；公告事實、選手回報、照片判讀及推論分開標示。
3. 將確認資料寫入對應 CSV／metadata／名單檔；不把未知比分、棄賽選手或簡章名額猜成參賽紀錄。
4. 執行預檢，先處理錯誤，再逐條核對提醒和筆數差異。
5. 建置生成頁面、資料、行事曆和更新摘要；檢視差異，避免意外覆蓋來源檔。
6. 預覽首頁及受影響的賽事詳情；涉及手機版面時再檢視窄螢幕。
7. 確認後提交並推送 `main`，等待 GitHub Pages 更新，再檢查公開頁面及資料版本。
